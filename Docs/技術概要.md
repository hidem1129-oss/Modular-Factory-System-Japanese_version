# 技術概要と実装資料への案内

このページでは、Modular Factory Systemの技術構成を日本語で説明し、仕様やコードを確認するための資料を案内します。全体の設計意図は[システム全体像](./システム全体像.md)、技術仕様と実装は[英語版リポジトリ](https://github.com/hidem1129-oss/Modular-Factory-System)で確認できます。

## 2. I²Cで何をやり取りするのか

各ノードは、ホストから読み書きできる共通のレジスタを公開しています。ここでいうレジスタは、ノード内部の情報や指示をアドレスごとに配置した通信上の窓口です。

現在の共通レジスタ領域は `0x00–0x3F` です。

| 領域 | 主な内容 |
|---|---|
| `0x00–0x0F` | モジュール種別、識別情報、リビジョン、対応機能 |
| `0x10–0x1F` | 状態、指示の受付結果、完了、非常停止、更新情報 |
| `0x20–0x2F` | フィードバック値、設定関連情報 |
| `0x30–0x3F` | 指示フラグ、動作モード、設定値、時間、制限値 |

モータとセンサでは実際の処理や値の意味が異なりますが、識別・指示・状態確認の共通部分をそろえています。すべてのノードがすべての設定項目を使うわけではありません。

典型的な動作指示は、次の順序です。

1. 動作パラメータを書き込む。
2. `LATCH_APPLY` を送り、準備した値を動作に使用する値として適用する。
3. 指示の受付結果を確認する。
4. `RUN` で動作を開始する。
5. `BUSY`、フィードバック、完了情報を確認する。
6. `READY` への復帰を確認する。

設定値の準備と適用を分けることで、書き込み途中の値で動作を始めない構成にしています。16ビットの値は上位バイト、下位バイトの順に転送します。

通信が成功しても、動作指示が受理されたとは限りません。動作中、設定未適用、非常停止中などの理由で拒否される場合があるため、通信結果と指示の受付結果を分けて確認します。

詳細：[レジスタ定義](https://github.com/hidem1129-oss/Modular-Factory-System/blob/main/Docs/Register_Map/Common_Register_Map.md)／[指示と設定値](https://github.com/hidem1129-oss/Modular-Factory-System/blob/main/Docs/Register_Map/Command_and_Setpoint.md)／[制御フロー](https://github.com/hidem1129-oss/Modular-Factory-System/blob/main/Docs/System_Architecture/Control%20Flow.md)

## 3. 共通ファームウェアと装置固有処理

ファームウェアは、共通部分とノード固有部分を組み合わせています。

| 共通部分が担当すること | ノード固有部分が担当すること |
|---|---|
| I²Cレジスタ、設定値の適用、指示の検証 | GPIOや周辺機能の初期化 |
| READY / BUSY / ESTOPの状態管理 | モータ、サーボ、センサの具体的な動作 |
| 開始・停止、完了情報、非常停止の管理 | 装置固有のパラメータ検証と完了条件 |
| ノード固有処理の呼び出し | フィードバック値の公開と装置の停止処理 |

装置固有の処理は、共通部分から呼び出す関数と公開APIを通じて接続します。新しい装置を追加する際も、通信や状態管理を毎回作り直さない構成です。

現在はPico SDKを使った協調型のポーリング処理で、I²Cは100 kHzです。ハードリアルタイムの動作保証を目的とした構成ではありません。

詳細：[状態モデル](https://github.com/hidem1129-oss/Modular-Factory-System/blob/main/Firmware/common/docs/State_Model.md)／[拡張API](https://github.com/hidem1129-oss/Modular-Factory-System/blob/main/Firmware/common/docs/Node_Extension_API.md)／[ノード追加手順](https://github.com/hidem1129-oss/Modular-Factory-System/blob/main/Firmware/common/docs/Adding_New_Node.md)

## 4. 状態監視と通信断の扱い

I²C DebuggerはPython / PyQt5の監視アプリです。ノードの状態とフィードバックを定期的に読み、画面表示とSQLiteへの保存を行います。

表示には `READY`、`BUSY`、`WARN`、`ERROR`、`ESTOP` に加えて、通信の観測結果を表す状態があります。

| 表示 | 意味 |
|---|---|
| UNKNOWN | 現在の状態を確定できない |
| No Device | 一度も応答を確認していないアドレスで、通信失敗がしきい値に達した |
| Signal Lost | 以前は応答していたノードで、通信失敗がしきい値に達した |

一度の読み取り失敗で即座に切断と判断せず、一時的な不確実さと継続的な通信断を区別します。ノードが公開する状態と、監視側が判定する通信状態も区別しています。

実機から読む `real` モードと、模擬データを使う `mock` モードがあります。mockでは状態変化や通信失敗を再現し、実機がなくても表示・状態判定・記録を確認できます。mockの動作確認だけで実機の電気的・機械的な動作を検証できるわけではありません。

詳細：[監視アプリの設計と動作](https://github.com/hidem1129-oss/Modular-Factory-System/blob/main/Software/I2C_Debugger/README.md)／[通信状態と変化検出の実装](https://github.com/hidem1129-oss/Modular-Factory-System/blob/main/Software/I2C_Debugger/debugger_model.py)／[表示状態の判定](https://github.com/hidem1129-oss/Modular-Factory-System/blob/main/Software/I2C_Debugger/node_logic.py)

## 5. 記録と電源監視

SQLiteには、状態変化、定期的な観測値、状態の継続期間、監視セッション、電源測定値などを保存します。

イベントは「何が変わったか」、スナップショットは「その時点で何を観測したか」、セッションは「どの実行で得た記録か」を確認するための情報です。Grafanaはこれらを読み、時系列や履歴として表示します。

電源監視ではTCA9548AでI²Cの接続先を切り替え、INA219から電圧・電流に関する測定値を取得し、電力を算出します。電源測定値はノードの通信状態とは別に表示・記録します。実測値から個々のノードのWARN状態へ自動的に対応付ける処理は、現時点では実装されていません。

詳細：[保存処理](https://github.com/hidem1129-oss/Modular-Factory-System/blob/main/Software/I2C_Debugger/db_logger.py)／[電源監視処理](https://github.com/hidem1129-oss/Modular-Factory-System/blob/main/Software/I2C_Debugger/power_monitor.py)／[GrafanaとSQLの説明](https://github.com/hidem1129-oss/Modular-Factory-System/blob/main/Software/Grafana/README.md)

## 8. 確認できる範囲と資料の優先順位

現在のシステムは卓上PoCです。ソフトウェア上の動作完了は、ワークの到達や押印品質など、物理的な結果の保証とは区別しています。安全認証、冗長化、本番向けセキュリティ、ハードリアルタイム保証も現在の対象範囲に含みません。

仕様説明と実装に差がある場合、現在の動作を確認する基準はソースコードです。レジスタと状態遷移は [node_core.h](https://github.com/hidem1129-oss/Modular-Factory-System/blob/main/Firmware/common/include/node_core.h) と [node_core.c](https://github.com/hidem1129-oss/Modular-Factory-System/blob/main/Firmware/common/core/node_core.c) を確認してください。古い表計算資料は補助的な設計参考資料として扱います。

設計理由は[設計時に考えたこと](./設計時に考えたこと.md)、実機で発見した課題は[実際に作って分かったこと](./実際に作って分かったこと.md)、判断の詳細は[Architecture Decision Log](https://github.com/hidem1129-oss/Modular-Factory-System/tree/main/ADL)で確認できます。
