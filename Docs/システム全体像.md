# システム全体像

## このページについて

このページでは、Modular Factory Systemがどのような要素で構成され、それぞれが何を担当しているのかを説明します。

詳細な通信仕様やレジスタ定義を説明することよりも、

* なぜシステムをこのように分けたのか
* どこで何を判断しているのか
* どの部分を変更すると、どこまで影響するのか
* 制御と監視をなぜ分けているのか

といった、システム全体の考え方を理解することを目的としています。

---

## 全体の構成

システムを大まかに見ると、次のように分かれています。

```text
                      Raspberry Pi 5
                            │
             ┌──────────────┴──────────────┐
             │                             │
        工程全体の制御                   状態監視
             │                             │
             ↓                             ↓
      共通の通信インターフェース         SQLite
             │                             │
             ↓                             ↓
        各制御モジュール                Grafana
             │
             ↓
      モータ・センサ・機構
```

一見するとRaspberry Pi 5を中心としたシステムですが、すべての処理をRaspberry Pi 5へ集約しているわけではありません。

工程全体の判断、装置ごとの細かな動作、状態監視、データ保存、過去データの表示をそれぞれ分けています。

この分け方によって、ある部分を変更したときに、関係のない部分まで変更しなくて済むことを狙っています。

---

## 役割を分けて考える

システム全体は、概ね次の役割に分けています。

| 役割       | 主に担当するもの              | 何をするか                |
| -------- | --------------------- | -------------------- |
| 物理的な工程   | コンベア、ゲート、紙送り、スタンプ機構など | 実際に物を動かす             |
| 電気的な接続   | 自作基板、配線、電源回路          | モータ、センサ、制御装置を接続する    |
| 装置ごとの制御  | Raspberry Pi Pico     | モータやセンサなどを個別に動かす     |
| 共通の制御ルール | Pico側共通ファームウェア        | 各モジュールを似た方法で扱えるようにする |
| 工程全体の制御  | Raspberry Pi 5(オーケストレーションプログラム)        | 複数装置をどの順番でどのように動かすか決める    |
| 状態監視     | I²C Debugger          | 各モジュールが現在どうなっているかを見る |
| 記録       | SQLite                | 状態やイベントを保存する         |
| 振り返り・可視化 | Grafana               | 保存された情報を後から確認する      |

重要なのは、これらが単に使用している技術の一覧ではなく、**責任の分け方**になっていることです。

---

## Raspberry Pi 5は「工程全体」を見る

Raspberry Pi 5側では、複数の装置を組み合わせた工程全体を扱います。

例えば仕分け工程なら、

```text
ワークを搬送する
        ↓
センサで到着を確認する
        ↓
カメラで色を確認する
        ↓
振り分け先を決める
        ↓
サーボのゲートを動かす
        ↓
再び搬送する
```

という流れがあります。

この「次に何を動かすか」という判断はRaspberry Pi 5側で行います。

一方で、Raspberry Pi 5がモータの端子を直接ON/OFFしたり、サーボへ直接細かな信号を生成したりする構成にはしていません。

その役割は各制御モジュールへ分けています。

---

## 制御モジュールは「自分の装置」を見る

各制御モジュールにはRaspberry Pi Picoを搭載しています。

制御モジュール側が担当するのは、

* モータを動かす
* サーボを指定位置へ動かす
* センサの値を取得する
* 停止要求を処理する
* 自分の状態を外部へ知らせる

といった装置単位の処理です。

考え方としては、

```text
Raspberry Pi 5
「次はこのモータを動かしてほしい」

        ↓

制御モジュール
「では、このモータをどう動かすかは自分が担当する」
```

という分担です。

Raspberry Pi 5は「次に何をするか」を判断し、制御モジュールは「自分に指示された処理をどう実行するか」を担当します。

この分け方にしたことで、同じモータ制御モジュールを別の工程でも利用できます。

---

## なぜ全部Raspberry Pi 5で制御しないのか

技術的には、Raspberry Pi 5からモータ、サーボ、センサを直接接続して制御することもできます。

その方が小規模な試作品では簡単な場合もあります。

しかし、その構成ではRaspberry Pi 5側のプログラムが、

* モータAの制御方法
* モータBの制御方法
* サーボの制御方法
* センサの読み方
* 各基板の接続方法

などをすべて知る必要があります。

装置が増えるほど、工程の制御プログラムとハードウェア固有処理が混ざっていきます。

そこで、このプロジェクトでは装置ごとの処理を制御モジュール側へ分離しました。

例えばモータの制御方法を変更しても、Raspberry Pi 5側から見た「モータへ動作を依頼する」という関係を維持できれば、工程全体のロジックまで大きく変更する必要がありません。

---

## 共通の通信方式を用意する

制御モジュールは、

* DCモータ
* サーボ
* センサ

など、接続しているものが異なります。

それでもRaspberry Pi 5側から似た方法で扱えるように、共通の通信インターフェースを用意しています。

例えば各モジュールは、

* 自分が何のモジュールなのか
* 現在動作中か
* 指示を受け付けられる状態か
* 動作が完了したか
* 取得した値は何か

といった情報を共通の形式で外部へ見せます。

その上で、モータの回転速度やサーボ角度など、装置ごとに必要な情報だけを追加します。

この構成によってRaspberry Pi 5側は、

```text
この装置はどういうICで、
どのGPIOにつながっていて、
どういう信号を送れば動くのか
```

というところまで毎回意識せず、

```text
このモジュールにこの処理を依頼する
```

という一段上の視点から工程を組み立てられるようにしています。

---

## 共通部分と装置固有部分も分ける

制御モジュールのファームウェア内部でも、さらに役割を分けています。

### 共通部分

モータでもセンサでも共通して必要になる、

* 通信
* 状態管理
* 指示の受付
* 実行開始・停止
* 非常停止状態
* 完了状態
* 外部へ情報を公開する仕組み

などを担当します。

### 装置固有部分

接続している装置によって異なる、

* モータの回し方
* サーボの動かし方
* センサの読み方
* 装置固有の完了条件
* 装置を安全側へ止める処理

などを担当します。

つまり、

```text
共通部分
「いつ処理してよいか」

        ↓

装置固有部分
「実際にどう動かすか」
```

という分担になっています。

新しい装置を追加するときに、通信や状態管理を毎回ゼロから作らないことを狙っています。

---

## 制御と監視は別の役割

このシステムでは、

**装置を動かすこと**

と、

**装置がどう動いているかを見ること**

を別の役割として考えています。

制御側は、

```text
工程全体の判断
        ↓
制御モジュールへ指示
        ↓
装置を動かす
```

という流れです。

一方、監視側は、

```text
制御モジュールの状態
        ↓
I²C Debuggerで観測
        ↓
SQLiteへ保存
        ↓
Grafanaで確認
```

という流れです。

Grafanaを見ながら装置を直接動かす構成にはしていません。

---

## なぜ制御と監視を分けるのか

監視画面が工程制御まで担当すると、画面やデータ保存方法を変更しただけで装置の動作へ影響する可能性があります。

このシステムでは、

* 工程を動かす
* 今の状態を見る
* 過去の状態を保存する
* 保存した結果を見やすく表示する

を分けています。

例えばGrafanaの表示方法を変更しても、モータ制御ファームウェアを変更する必要はありません。

逆にモータの制御方法を変更しても、共通して公開している状態情報が変わらなければGrafana側まで作り直す必要はありません。

このように、変更理由の異なるものを分けておくことで、変更の影響範囲を小さくしています。

---

## 「見えている状態」と「実際の物理状態」は同じではない

監視システムで確認できるのは、制御モジュールが外部へ公開している情報です。

例えば、

* モータ制御が完了した
* サーボへの指示が完了した
* センサ値が変化した
* 通信が続いている

といったことは確認できます。

しかし、それだけで必ずしも、

* ワークが目的地へ到達した
* 物が詰まっていない
* スタンプが十分な力で押された
* ゲートが想定どおりの角度まで実際に動いた

ことまで証明できるわけではありません。

例えばモータへ「一定時間回転する」という指示を出し、ソフトウェア上では正常終了していても、途中でワークが物理的に引っ掛かっている可能性は残ります。

そのため、

**ソフトウェア上で観測できる状態と、実際の物理現象は区別して考える**

ようにしています。

必要であれば、追加のセンサやカメラなどを使って物理状態を確認する必要があります。

---

## SQLiteは「後から見られる状態」を作る

動いている装置をその場で見るだけでは、後から原因を確認することが難しくなります。

そこで、一部の状態をSQLiteへ保存しています。

例えば、

* 状態が変化した時刻
* 各モジュールの状態
* 監視を行った期間
* 電圧・電流・電力
* イベント履歴

などを残します。

これによって、

```text
「今動いているか」
```

だけでなく、

```text
「さっき何が起きていたか」
```

も確認できるようにしています。

---

## Grafanaは「過去を読みやすくする」

SQLiteへ保存した情報は、そのままでは人が確認しにくいため、Grafanaで可視化しています。

Grafanaでは、

* 状態の時系列
* イベント履歴
* 電源状態の変化

などをグラフとして確認できます。

ここでもGrafana自身が装置の状態を決めるわけではありません。

Grafanaは、すでに記録された情報を人が理解しやすい形へ変換する役割です。

---

## Raspberry Pi 5を使っていても、すべてを一体化しているわけではない

工程制御、状態監視、SQLite、Grafanaなどは、現在のPoCでは同じRaspberry Pi 5上で動かすことができます。

しかし、

**同じコンピュータ上で動いていることと、同じ責任を持っていることは別**

と考えています。

例えば、

* 工程制御プログラム
* I²C Debugger
* SQLite
* Grafana

は論理的には別の役割です。

PoC規模では、これらを別々のPCやサーバへ分離すると構成が必要以上に大きくなります。

そのため、物理的にはまとめつつ、ソフトウェア上の責任は分離しています。

---

## 物理機構も交換可能な部分として考える

このシステムでは、制御側だけでなく物理機構についても、工程ごとに交換できる部分として扱っています。

例えば、

### 色分け仕分け

* コンベア
* ワーク検出
* カメラ
* 振り分けゲート

を使用します。

### スタンプ工程

* 紙送り
* スタンプ機構
* 異なる工程順序

を使用します。

2つの工程では物理的な構成がかなり異なります。

一方で、

* Raspberry Pi 5
* 制御モジュール
* 通信方式
* 監視
* SQLite
* Grafana

などは共通して利用できます。

物理的な工程を交換しても、共通部分をなるべく再利用することがこのシステムの狙いの一つです。

---

## 変更するときの考え方

この構成では、変更内容によって主に触る場所を分けることを狙っています。

| 変更したいこと      | 主に変更する場所             |
| ------------ | -------------------- |
| 工程の順番を変える    | Raspberry Pi 5側の工程制御 |
| モータの動かし方を変える | モータ用制御モジュール          |
| 新しいセンサを追加する  | センサ側ハードウェア・ファームウェア   |
| 物理工程を変える     | 機構と工程制御              |
| 保存するデータを増やす  | 監視・SQLite側           |
| グラフの見せ方を変える  | Grafana              |
| 基板の接続方式を変える  | ハードウェアと関連する通信条件      |

完全に影響をゼロにできるわけではありません。

ただし、

**変更理由が違うものをなるべく別の場所へ閉じ込める**

ことを基本方針としています。

---

## すべてを汎用化しているわけではない

このシステムでは再利用や組み替えを重視していますが、何でも自由に接続できる万能システムを目指しているわけではありません。

例えば、

* 接続できる装置
* 配線距離
* モジュール数
* 機構サイズ
* 通信速度
* 電源容量

には現在の実装上の制約があります。

卓上PoCとして必要な範囲で共通化し、それを超える機能は必要になった時点で再評価する方針です。

---

## この構成で確認したかったこと

このシステム構成で確認したかったのは、個々の部品の性能ではなく、

* 複数の技術領域を一つのシステムとして接続できるか
* 装置ごとの処理と工程全体の判断を分離できるか
* 制御と監視を分離できるか
* 異なる工程で共通基盤を再利用できるか
* 変更の影響範囲を限定できるか
* 実際の物理動作を見ながらシステム構成を議論できるか

という点です。

このプロジェクトでは、最終的な工場設備を完成させることよりも、

**「実際に動くシステムを使って、構成や責任分担が妥当かを確認すること」**

を優先しています。
